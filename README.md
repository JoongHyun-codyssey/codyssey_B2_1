# Budget App

Python으로 구현하는 파일 입출력 기반 나만의 용돈 기입장입니다. 수입과 지출을 기록하고, 검색·월별 요약·예산 관리 기능을 통해 거래 내역을 관리합니다.

**[프로젝트 실행 결과와 기능별 스크린샷 보기](docs/results.md)**

**[입력값 검증 및 예외 상황 처리 결과 보기](docs/validation.md)**

## 1. 학습 목표

- JSONL 파일 기반 데이터 영구 저장과 CRUD 구현
- 모델·저장소·서비스·CLI의 역할 분리
- `yield` 기반 제너레이터를 이용한 파일 스트리밍 처리
- 데코레이터를 이용한 로그·예외 처리·실행 시간 측정 분리
- 타입 힌트와 `dataclass`를 활용한 데이터 구조 및 입출력 계약 명확화

## 4. 실행 방법

Python 3.10 이상을 개발 기준으로 사용하며, 초기 구현은 표준 라이브러리만 사용할 예정입니다. 실제 검증한 Python 버전은 구현 후 추가합니다.

프로젝트 최상위 폴더에서 실행합니다.

```bash
python -m budget_app --help
python -m budget_app add
```

환경에 따라 `python` 대신 `python3`를 사용합니다. 모든 명령 및 하위 명령에서 `--help`를 지원하도록 구현합니다.

저장 폴더 변경 옵션은 명령어 앞에 지정합니다.

```bash
python -m budget_app --data-dir ./custom-data list
```

## 5. 주요 명령 예시

아래는 구현 예정 인터페이스입니다. `<id>`는 실제 거래 ID로 바꿉니다.

```bash
# 거래 추가: 날짜, 타입, 카테고리, 금액, 메모, 태그를 순서대로 입력
python -m budget_app add

# 거래 목록: 기본 10건
python -m budget_app list --limit 10

# 조건 검색: 함께 지정한 조건은 모두 만족해야 함
python -m budget_app search --from 2026-09-01 --to 2026-09-30
python -m budget_app search --category food --type expense
python -m budget_app search --q 점심 --tag 외식

# 거래 수정: 대화형 기반
python -m budget_app update --id <id>

# 거래 삭제
python -m budget_app delete --id <id>

# 월별 요약: TOP 기본 5개
python -m budget_app summary --month 2026-09 --top 5

# 월별 예산 설정 및 조회
python -m budget_app budget set --month 2026-09 --amount 500000
python -m budget_app budget show --month 2026-09

# 카테고리 관리: 추가·삭제할 이름은 대화형으로 입력
python -m budget_app category add
python -m budget_app category list
python -m budget_app category remove

# CSV 가져오기
python -m budget_app import --from ./transactions.csv

# CSV 내보내기: 월 또는 시작일·종료일 쌍 중 하나를 필수 지정
python -m budget_app export --out ./september.csv --month 2026-09
python -m budget_app export --out ./period.csv --from 2026-09-01 --to 2026-09-15
```

`update`는 `--date`, `--type`, `--category`, `--amount`, `--memo`, `--tags`를 지원할 예정입니다. 메모는 `--memo ""`, 태그는 `--tags ""`로 비우며, 태그가 여러 개이면 `--tags "외식,점심"`처럼 입력합니다.

## 6. 데이터 저장 형식

기본 저장 위치는 실행한 작업 디렉터리 기준 `./data`입니다. 파일과 폴더가 없으면 첫 실행 시 자동 생성합니다. 저장 형식은 JSONL로 통일하며, 한 줄에 하나의 JSON 객체를 저장합니다.

### 6-1. JSONL VS CSV

| 비교 | JSONL | CSV |
|---|---|---|
| 형태 | 한 줄에 JSON 객체 하나 | 행/열 형태 |
| 사람이 읽기 | 비교적 쉬움 | 매우 쉬움 |
| Python 자료형 | 잘 보존됨 | 대부분 문자열로 읽힘 |
| 리스트 저장 | 편함 | 별도 규칙 필요 |
| 구조 변경 | 유연함 | 상대적으로 불편 |
| 엑셀 호환 | 불편 | 매우 좋음 |
| 대용량 순차 처리 | 좋음 | 좋음 |
| 프로그램 내부 저장 | **적합** | 가능하지만 덜 편함 |
| 가져오기/내보내기 | 가능 | **매우 적합** |

JSONL = 프로그램이 데이터를 저장하기 편한 형식
CSV = 사람이 엑셀 등으로 데이터를 확인 및 교환하기 편한 형식

이러한 점을 고려하여 이번 미션에서는 엑셀등을 이용하지 않았기 때문에 JSONL로 데이터를 저장하기 편하게 하기 위하여 JSONL을 선택했습니다.


### 거래: `transactions.jsonl`

```json
{"id":"example-id-001","type":"expense","date":"2026-09-17","amount":10000,"category":"food","memo":"점심","tags":["외식"]}
```

| 필드 | 형식 및 규칙 |
| --- | --- |
| `id` | 고유 문자열, 신규 거래 생성 시 UUID 사용 예정 |
| `type` | `income` 또는 `expense` |
| `date` | 실제 존재하는 날짜, `YYYY-MM-DD` |
| `amount` | 원 단위 양의 정수 |
| `category` | 등록된 카테고리 이름 |
| `memo` | 문자열, 기본값은 빈 문자열 |
| `tags` | 문자열 목록, 기본값은 빈 목록 |

### 카테고리: `categories.jsonl`

```json
{"name":"food"}
{"name":"salary"}
```

빈 카테고리 파일에는 category add를 먼저 하도록 안내하고 add를 막았습니다.

### 예산: `budgets.jsonl`

```json
{"month":"2026-09","amount":500000}
```

예산 금액은 양의 정수이며, 같은 월에 다시 설정하면 기존 예산을 갱신합니다. 사용률은 `해당 월 총지출 / 예산 × 100`으로 계산합니다. 지출이 예산보다 클 때 초과 경고를 표시하며, 거래가 없는 달은 데이터 없음을 명시합니다.

## 7. CSV import/export 스키마

> 과제 원문에 명시된 최소 CSV 스키마를 확인한 뒤 아래 설계와 대조하여 확정해야 합니다.

UTF-8 인코딩을 사용하며, import 시 UTF-8 BOM이 포함된 파일도 읽을 수 있습니다.

첫 줄의 헤더는 `column,required,설명`입니다.
거래 한 건은 `id` 행부터 시작하는 7개 행으로 저장합니다.

- `column`: 거래 필드 이름
- `required`: 필수 값 여부 (`Y`: 필수, `N`: 빈 값 허용)
- `설명`: 해당 필드의 실제 거래 값

```csv
column,required,설명
id,Y,f1a27c93-6b84-4d15-9e02-c83b7a406d51
date,Y,2026-09-21
type,Y,income
category,Y,food
amount,Y,9000
memo,N,점심 김치찌개
tags,N,"점심, 외식"
```

여러 거래는 위 구조를 반복하여 저장합니다.
`memo`와 `tags`는 값이 없어도 행을 유지합니다.

파일 마지막에는 다음 안내 행을 추가하며, import 시 건너뜁니다.

```csv
"공통: UTF-8, 헤더 포함",,
```

- 헤더는 `column`, `required`, `설명`의 3개 열로 고정합니다.
- 거래 한 건은 `id` 행으로 시작하며, `id`, `date`, `type`, `category`, `amount`, `memo`, `tags`의 7개 필드로 구성합니다.
- `required`는 `memo`와 `tags`에 `N`, 나머지 필드에 `Y`를 사용합니다.
- `memo`와 `tags`는 값을 비워도 되지만 해당 행은 유지해야 합니다.
- `tags`는 쉼표(`,`)로 구분하며, 개별 태그 내부의 쉼표는 허용하지 않습니다.
- 쉼표·줄바꿈·따옴표가 포함된 값은 Python `csv` 모듈의 CSV 인용 규칙에 따라 처리합니다.
- 가져올 때 `id`는 필수이며, 입력된 값을 유지합니다.
- 파일 마지막에 `공통: UTF-8, 헤더 포함` 안내 행을 추가하며, 가져올 때는 해당 행을 건너뜁니다.
- 내보낸 건수는 CSV 행 수가 아닌 거래 건수를 기준으로 계산합니다.

## 8. 데이터 안전성과 구현 방침

- 파일은 `yield` 기반 제너레이터로 한 줄씩 읽고 처리합니다.
- 수정·삭제는 같은 폴더의 임시 파일에 결과를 기록한 뒤 `os.replace()`로 교체합니다. 기록 중 실패하면 원본을 유지하도록 설계합니다.
- 읽기 중 손상된 JSON이나 잘못된 저장 데이터를 만나면 위치를 안내하고 중단합니다. 손상된 행을 조용히 누락한 채 재저장하지 않습니다.
- 날짜·금액·타입·카테고리를 검증하고, 존재하지 않는 ID는 사용자 메시지로 처리합니다.
- 예외 처리는 CLI 경계에서 사용자에게 안내하고, 저장 계층의 실패를 성공으로 처리하지 않습니다.
- 여러 프로세스의 동시 쓰기는 초기 지원 범위에서 제외하며, 한 번에 한 프로세스만 실행하는 것을 전제로 합니다.

### 최신순과 스트리밍

최신순의 기준은 거래 날짜 내림차순으로 정하고, 같은 날짜에서는 ID로 순서를 고정할 예정입니다. 파일에 추가된 순서가 거래 날짜순이라는 가정은 하지 않습니다.

`list --limit N`은 파일을 순회하면서 최신 N건만 보관하는 방식을 검토합니다. 검색 결과 전체를 최신순으로 출력하는 방법은 구현 전 확정할 항목입니다. 단순히 `sorted()`로 결과 전체를 메모리에 모으는 방식은 엄격한 스트리밍 요구를 충족하지 못하므로, 날짜순 저장 유지 또는 외부 정렬 같은 방식을 검토합니다.

### 병목현상과 개선방안

현재 `search` 기능은 조건에 맞는 거래 내역을 검색한 뒤 최신순으로 정렬하여 출력한다. 데이터가 100k(10만 건) 수준으로 증가하면 전체 파일 탐색과 정렬 과정에서 성능 및 메모리 사용량 문제가 발생할 수 있다.

예를 들어 다음과 같이 식비 카테고리를 검색한다고 가정한다.

```bash
search --category 식비
```

전체 거래 데이터가 100,000건이고, 이 중 조건에 맞는 거래가 70,000건이라면 일반적인 전체 정렬 방식은 다음과 같이 동작한다.

```text
100,000건 파일 읽기
        ↓
100,000건 JSON 파싱
        ↓
조건에 맞는 70,000건 검색
        ↓
70,000건 메모리에 저장
        ↓
70,000건 최신순 정렬
        ↓
결과 출력
```

전체 데이터 수를 `n`, 검색 결과 수를 `k`라고 하면 시간 및 공간 복잡도는 다음과 같다.

- 검색: `O(n)`
- 정렬: `O(k log k)`
- 메모리 사용량: `O(k)`

최악의 경우 모든 데이터가 검색 조건에 해당한다면 `k = n`이 되므로 정렬에 `O(n log n)`, 메모리에 `O(n)`이 필요하다.

100,000건을 기준으로 하면 다음과 같이 볼 수 있다.

```text
검색       : O(100,000)
정렬       : O(100,000 log 100,000)
메모리     : O(100,000)
```

![Big-O_complexity](/image/Big-O%20complexity.png)

100k 수준에서는 일반적인 환경에서 `sorted()` 자체가 반드시 심각한 성능 문제를 발생시키는 것은 아니다. 하지만 검색 결과 전체를 메모리에 적재해야 하기 때문에 데이터가 증가할수록 메모리 사용량도 함께 증가하며, 전체 데이터를 메모리에 올리지 않는 스트리밍 처리 요구사항을 충족하기 어렵다.

따라서 다음과 같은 병목 지점과 개선 방안을 고려할 수 있다.

| 병목 | 원인 | 개선 방안 |
|---|---|---|
| 전체 파일 스캔 | JSONL에 검색 인덱스가 없어 매번 전체 데이터를 확인해야 함 | 별도 인덱스 구축 또는 DB 도입 |
| JSON 파싱 | 검색할 때마다 최대 100k건에 대해 `json.loads()` 수행 | 캐시 또는 DB 활용 |
| 전체 정렬 | `sorted()` 사용 시 검색 결과 전체를 메모리에 저장해야 함 | 외부 정렬(External Sort) 적용 |
| 임시 파일 I/O | 외부 정렬 과정에서 chunk 파일의 쓰기/읽기 발생 | 적절한 chunk 크기 설정 |
| ID 검색 | `update`, `delete` 수행 시 원하는 ID를 찾기 위해 전체 탐색 필요 | ID 인덱스 구축 |
| update/delete | JSONL 파일 중간 데이터를 직접 수정하기 어려움 | 파일 재작성 또는 DB 도입 |
| 메모리 사용량 | 검색 결과를 리스트로 만들면 결과 수에 비례해 메모리 증가 | Generator와 chunk 단위 처리 |

특히 전체 검색 결과를 최신순으로 출력해야 하는 경우에는 **외부 정렬(External Sort)**을 적용할 수 있다.

검색 결과를 모두 메모리에 저장하지 않고 일정한 크기의 chunk로 나누어 처리한다. 예를 들어 1,000건씩 메모리에 저장한 뒤 `(date, id)` 기준으로 정렬하여 임시 파일에 기록한다.

```text
JSONL 파일 순차 탐색
        ↓
검색 조건 확인
        ↓
1,000건씩 메모리에 저장
        ↓
(date, id) 기준 정렬
        ↓
임시 chunk 파일 생성
        ↓
각 chunk를 병합
        ↓
최신순으로 결과 출력
```

이 방식을 사용하면 전체 검색 결과가 100,000건이어도 메모리에 모든 결과를 동시에 보관할 필요가 없다. 각 chunk를 정렬한 후에는 k-way merge 방식으로 정렬된 임시 파일들을 병합하여 최종 결과를 순차적으로 출력할 수 있다.

따라서 현재 프로젝트에서는 JSONL과 Generator를 이용한 스트리밍 구조를 유지하면서, `list --limit N`에는 크기가 제한된 heap을 사용하고 전체 검색 결과의 최신순 출력에는 chunk 기반 외부 정렬을 적용하는 방법을 고려할 수 있다.

향후 데이터 규모가 더욱 증가하거나 `update`, `delete`, ID 검색 등의 임의 접근이 빈번해진다면 별도의 인덱스를 구축하거나 SQLite와 같은 데이터베이스로 전환하는 것이 더 적합하다.
